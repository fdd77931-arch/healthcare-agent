# 「循迹」健康行动分层助手 PRD

## 1. 文档状态与证据边界

- 版本：MVP 演示原型（0.1.0）
- 产品定位：帮助用户整理症状信息、判断下一步行动；不是诊断或治疗工具。
- 当前证据：120 条完全合成的、可重复运行的产品测试案例；不包含真实患者或临床结局。
- 安全状态：红旗召回率为 92%（46/50），低于预设 98% 门槛，**安全门槛未通过**；不可作为临床有效或可投入实际使用的证明。

本 PRD 将“已实现”与“计划验证”分开描述。实现依据是当前 Web、API、领域逻辑和离线评测报告；用户访谈尚未完成。

## 2. 问题

身体不适时，用户往往先搜索或询问通用 AI，却得到大量可能原因，仍难回答三个行动问题：现在是否紧急、何时去哪里就医、就诊前该准备什么。信息零散和不确定性容易放大焦虑，也可能让用户延迟人工医疗评估。

「循迹」不回答“得了什么病”，而是用有限追问把现有信息转化为行动分层、时间窗口、就诊准备和升级条件。风险信号优先于常规对话：任一轮命中固定红旗后，普通流程必须中断。

## 3. 目标用户与待验证假设

首要画像是 20–35 岁、习惯用手机先搜索或询问 AI 的城市职场人。其可能在工作间隙处理突发不适，缺乏医学训练，又担心遗漏严重风险或过度就医。

这是探索性画像，不是研究结论。计划通过 3–5 次访谈验证以下假设：

- 用户愿意描述症状，但希望每个追问都能解释用途。
- 用户需要可复述的“何时、去哪、做什么”，而非疾病名称。
- 用户会在信息不足、症状加重或出现高风险表现时接受转人工医疗渠道。
- 用户会关注是否留存原始症状文本及是否可以清除本次记录。

### Jobs to Be Done

当我突然感到不适、又不确定严重程度时，我想用短时间整理关键表现和风险信号，从而决定我应该立即求助、尽快就医、预约门诊还是短期观察。

## 4. 目标与非目标

### 目标

1. 先识别固定高风险表现，再进行有限的信息补充。
2. 在正常路径内形成四类行动建议：立即急救、尽快就医、近期门诊、短期观察；信息不足时明确降级。
3. 输出结构化、可复制的就诊参考摘要，说明已知、未知和升级条件。
4. 用匿名、短时会话与允许列表事件记录，减少不必要的健康信息留存。
5. 以可审计的合成案例持续暴露安全和语言边界缺陷。

### 非目标

- 疾病诊断、患病概率、处方、剂量或治疗方案。
- 医院/医生推荐、挂号交易、支付、账号体系或长期健康档案。
- 真实病历接入、医学影像分析、临床决策支持或医疗机构背书。
- 将合成离线结果解释为真实人群表现、临床准确率或上线资格。

## 5. 当前范围与实现映射

| 用户能力 | 当前实现 | 入口或接口 |
| --- | --- | --- |
| 自由文本开始评估 | 单页主诉表单与匿名会话创建 | `app/web/index.html`；`POST /api/sessions` |
| 每轮红旗中断 | 固定规则在 `advance` 中执行，命中返回 `emergency` | `app/domain/red_flags.py`；`app/domain/triage.py` |
| 有限追问 | 固定槽位顺序、一次一个问题、上限 6 个问题 | `app/domain/questions.py`；`app/domain/triage.py` |
| 行动分层与结构化结果 | 五种状态：`emergency`、`urgent`、`routine`、`self_monitor`、`insufficient` | `app/domain/models.py`；`app/domain/triage.py` |
| 结果、急症与信息不足界面 | 独立界面状态，急症使用固定 `tel:120` | `app/web/app.js` |
| 就诊参考摘要 | 后端仅返回允许列表中的归一化槽位摘要，前端按固定模板拼接并支持复制 | `app/api.py`；`app/domain/triage.py`；`app/web/app.js` |
| 清除会话与固定标签反馈 | 删除匿名会话；反馈只接受受控标签 | `DELETE /api/sessions/{id}`；`POST /api/feedback` |
| 输出安全检查 | 拒绝诊断、剂量、治疗措辞及不一致时间窗 | `app/domain/safety.py` |

当前默认演示模式使用本地 `DemoSlotParser`；没有启用外部模型服务或模型 API 调用。

## 6. 核心用户故事

- 作为出现不适的用户，我希望先知道是否需要立即行动，避免把高风险表现留在长对话里。
- 作为不确定该怎么描述的人，我希望一次只回答一个与行动等级有关的问题。
- 作为准备就医的人，我希望复制一段摘要，减少临场遗漏。
- 作为重视隐私的人，我希望不登录也能使用，并可清除本次匿名会话。
- 作为信息不足的用户，我希望系统明确说出不确定性并指向人工医疗渠道，而不是猜测。

## 7. 核心流程

1. 用户在首页阅读“行动建议，不是诊断”的边界，输入主诉并开始评估。
2. API 解析当前文本、更新槽位，并将本轮与有限历史交给状态机。
3. 状态机先执行红旗规则；若命中，返回紧急结果，前端聚焦急症标题并提供固定 `120` 入口。
4. 未命中红旗时，系统按主症状、起始时间、严重程度、伴随症状、趋势、风险因素的顺序选择一个缺失项追问；已识别风险背景会阻止短期观察，最低采用更保守的近期门诊建议。
5. 信息充分时生成结构化行动结果；达到问题上限、出现冲突或仍有关键未知时返回 `insufficient`。
6. 安全校验通过后，前端按固定字段展示行动等级、时限、科室、未知项、升级条件和就诊参考摘要。
7. 用户可复制摘要、提交固定标签反馈、清除匿名会话，或在网络失败时保留输入并重试。

## 8. 信息架构

```text
首页 / 主诉输入
├── 追问（最多 6 个）
├── 急症行动页（任意轮红旗中断）
├── 常规结果页（尽快就医 / 近期门诊 / 短期观察）
├── 信息不足页
└── 错误与重试状态
```

单页 Web 通过 `start-state`、`followup-state`、`emergency-state`、`result-state`、`insufficient-state` 和 `error-state` 切换这些状态；这不是多页账户流程。

## 9. 功能需求与异常状态

### 功能要求

- 每次仅提出一个固定目录中的问题，并显示提问理由与进度。
- 红旗规则必须优先执行；高风险状态不能被普通分层降级。
- 最终结果必须包含行动等级、时间窗口、科室、依据、未知项、升级信号、就诊摘要和免责声明。
- 用户/API 文本使用安全的文本节点渲染，不能作为 HTML 注入页面。
- 请求进行中禁止重复提交；成功渲染前不清空用户输入。

### 异常与降级

| 情况 | 当前处理 |
| --- | --- |
| 首轮或后续轮命中红旗 | 中断追问，展示固定急症操作与免责声明。 |
| 关键槽位缺失或信息冲突 | 返回 `insufficient`，提示需要人工医疗确认。 |
| 达到 6 个问题仍无法可靠分层 | 不强行给出常规行动等级，返回 `insufficient`。 |
| 结果含禁用措辞或时间窗冲突 | `validate_result` 拒绝该结果。 |
| 请求失败、会话过期或响应不完整 | 前端保留已填写内容，提供重试或返回修改。 |
| 外部模型不可用 | 当前默认模式不依赖外部模型；未来接入必须保留本地安全规则、超时与降级策略。 |

## 10. 安全、隐私与可访问性

安全规则是词组级、确定性的演示基线，不是临床判断。当前评测中 4 条错别字/变体隐晦红旗未命中，因此不能降低风险叙述或扩大使用范围。结果安全门还会拦截确定性诊断、用药剂量和治疗指令，并检查行动等级与时间窗口是否矛盾。

- 不要求姓名、电话、证件或账号；页面提示不要输入可识别身份信息。
- `SessionStore` 仅在内存中保存匿名会话，默认 TTL 为 30 分钟；删除接口可清除当前会话。
- 为跨轮红旗检查，状态机短时保留最多 8 轮、每轮最多 240 字的用户安全证据；它不经 API 返回，也不属于分析事件。
- `EventRecorder` 只记录匿名会话 ID、受控问题 ID、轮次、行动等级和固定反馈标签，不记录原始症状文本。
- 界面提供键盘焦点、状态播报、最小点击区和减少动态效果支持；急症页将焦点移到行动标题。

## 11. 分析与指标

### 当前匿名事件

`session_created`、`message_received`、`session_deleted`、`feedback_submitted`。当前事件枚举位于 `app/services/analytics.py`；它们用于流程调试，不应被解释为用户规模、留存或满意度数据。

### 计划验证的产品指标

| 指标 | 定义 | 当前状态 |
| --- | --- | --- |
| 红旗召回率 | 标记红旗案例中由生产状态机返回 `emergency` 的比例 | 92%（46/50），未达到 98% 门槛 |
| 行动等级准确率 | 合成案例中行动等级与产品测试标签一致的比例 | 90%（108/120） |
| 边界措辞通过率 | 输出校验、必含和禁用措辞契约均满足的比例 | 90%（108/120） |
| 结果复述率 | 参与者能说清何时、去哪、做什么的比例 | 计划通过访谈/任务测试验证 |
| 漏斗与退出 | 开始、完成、复制摘要、反馈的匿名事件链路 | 当前事件不足以完整计算，需先完成事件设计评审 |

## 12. 验收标准

### 已实现可回归验证

- API 能创建、追加和删除匿名会话，并且公开响应不回传原始用户消息或内部安全证据；就诊摘要仅包含允许列表中的归一化槽位。
- 红旗可在首轮或后续轮触发紧急状态；常规追问不超过 6 个问题。
- 输出结构满足 `TriageResult` 固定字段，并经禁用措辞与时间窗一致性检查。
- Web 覆盖开始、追问、急症、结果、信息不足、错误与重试状态；失败后保留输入。
- 120 条合成案例归一化后保持唯一，评测脚本可离线重复运行。

### 尚未达成的发布前条件

- 红旗召回率达到或超过预设 98% 门槛，并复测错别字、口语变体和跨轮否定场景。
- 由合格临床人员独立审查高风险规则、边界和测试方案。
- 完成 3–5 名目标用户访谈与任务测试，验证边界理解、追问负担和结果复述。
- 完成隐私、安全、运营响应和真实使用场景的发布评审。

## 13. 后续路线

先修复已知错别字/变体红旗漏检与轻症信息抽取缺口，再扩展对抗回归案例。之后才评估可替换的模型解析器；它仅可把用户语言解析为槽位，不能生成结果、替代规则兜底或绕过输出校验。任何扩展都应先重新运行完整离线评测，并以访谈和临床审查结果决定是否继续。
